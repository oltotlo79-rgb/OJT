# 公開後CI失敗の原因と再発防止

## 失敗ログ

- `35667168471` / `35667226200`: `fs-atomic.test.ts` の一時ロック解放テストでEPERM。
- `35667511194`: 同じテストで5秒タイムアウト。
- 3実行とも残る174ファイル・3,041テストは成功。以前の成功実行`35664592859`には、画面撮影のUnknownVizErrorによるテスト再実行が1件あった。

## 原因

ロック解放用PowerShellプロセスへファイルで指示した後、100msのsleepで解放されることを期待していた。実際のスケジューリングが製品の再試行予算350msに収まる保証はなく、外部プロセスの起動・終了も既定5秒に含まれていた。stdinを同期ファイル信号へ置き換えるだけでは不十分だった。

さらに、先行コミットのCI成功でリリースを進め、その後のmain・タグのCI完了を待たなかった。公開対象のSHA自体を確認する自動ゲートが欠けていた。

## 物的対策

1. 実ファイルのロックを保持したまま最初のrenameを実行し、再試行の待機点で解放信号を出して、ハンドルを閉じた印まで待つ。ファイル操作はモックしない。最初の再試行が50ms指定であること、保持が続く場合は50/100/200msで打ち切ることも検証する。
2. 外部プロセスの準備・解放・終了待ちに個別の上限を設ける。準備失敗・検証失敗でも終了処理を通し、子プロセスのエラーを捨てない。製品の待機時間は延長しない。
3. 撮影準備の失敗だけに限定した待機を追加し、他のエラーは即座に失敗させる。E2E全体の再実行は0回、失敗トレースは初回から保存。
4. `pnpm release:publish` を公開経路とし、対象SHAのmain・タグの最新CIと添付EXEのハッシュ一致を必須にする。古い成功・失敗・中断・未完了・添付不一致を拒否するテストをCIとpush前に実行。
5. 既存のv1.1.0タグと配布物を差し替えず、新しいv1.1.1で公開する。

作業は既存のOJT内worktreeで実施。Git名義・認証アカウントは変更していない。
